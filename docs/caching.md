# 本地缓存与响应速度优化

适用：`env_inspection_desktop`（Electron 22.3.27 + Vue3 + ElementPlus）

## 一、成果（真实网关实测）

模拟仪表盘首屏取数（`stats()` + `messages()` + `hazards()`）：

| 场景 | 耗时 | 网络请求 | 下载量 |
|---|---:|---:|---:|
| 冷启动（无缓存） | 3403 ms | 3 次 | 1692 KB |
| 再次进入（命中缓存） | **2 ms** | **0 次** | 0 KB |

## 二、瓶颈定位（优化前实测数据）

| 集合 | 耗时 | 数据量 | 条数 |
|---|---:|---:|---:|
| `message` | **1706 ms** | **1447 KB** | 973 |
| `hazards` | 1547 ms | 191 KB | 123 |
| `users` | 340 ms | 51 KB | 182 |
| `departments` | 170 ms | 3 KB | 29 |

### 发现的结构性浪费：同一份数据被重复拉取三次

仪表盘首屏与启动流程中，`message` 集合（1.4MB / 约 1.7 秒）被**全量拉取三次**，而三次拿的是完全相同的数据：

1. `app.js` 启动时 `api.messages({ read:'false' })` 取未读数
2. `api.stats()` 内部为统计未读数再拉一次
3. `dashboard.js` 的 `api.messages({})` 又拉一次

合计约 5 秒、4.3MB 的重复开销。接入缓存后三者共享同一份数据，只发一次请求。

## 三、实现方案

新增 `app/js/cache.js`（内存 + localStorage 双层），`api.js` 的集合查询统一走该缓存。

### 核心机制

| 机制 | 说明 |
|---|---|
| **双层缓存** | 内存（同进程零成本）+ localStorage（跨重启保留，冷启动首屏即时渲染） |
| **并发去重** | 相同 key 的并发请求只真正发一次网络请求 |
| **TTL** | 隐患/消息/公告 60 秒；用户 5 分钟；部门 10 分钟 |
| **SWR** | 见下方"重要语义"，仅对磁盘残留数据生效 |
| **写操作失效** | 所有增删改操作后失效对应集合，避免界面看到改前的数据 |
| **登录后预热** | `api.warmCache()` 后台预取各集合，之后切换页面即时响应 |
| **容量保护** | 单条超 2MB 不落盘；配额不足时淘汰最旧的一半 |
| **降级容错** | localStorage 不可用（隐私模式/禁用）时自动退化为纯内存缓存 |

### 缓存键设计

缓存的是**集合原始数据**，筛选与分页仍在前端完成。因此不同参数的调用（如按状态过滤、分页）可以共享同一份缓存，而不是每个查询条件各存一份。

键格式：`col:<集合名>:<稳定序列化后的查询条件>`。
稳定序列化会按键名排序，避免"内容相同但键顺序不同"生成两份缓存。

### 各集合缓存策略

| 集合 | TTL | 是否持久化 | 理由 |
|---|---:|:--:|---|
| `hazards` | 60 s | 是 | 变动较频繁 |
| `message` | 60 s | 是 | 数据量最大，收益最高 |
| `announcement` | 60 s | 是 | 公告需及时可见 |
| `users` | 5 min | **否** | 见下方安全说明 |
| `departments` | 10 min | 是 | 极少变动 |

### ⚠️ 重要语义：SWR 只用于冷启动

**会话内**的过期数据走**阻塞刷新**，**磁盘**（上一会话残留）的过期数据走 **SWR**（先返回旧值 + 后台刷新）。

原因：如果无差别应用 SWR，用户点击「刷新」按钮时会拿到旧值，看起来像刷新没生效。区分二者后：

- 冷启动：先用磁盘旧数据立刻渲染出界面，再后台刷新 → 首屏无白屏
- 点「刷新」：一定发起网络请求拿到新数据 → 符合预期

此外，各视图的「刷新 / 重置」按钮都会先调用 `api.refreshCache(集合名)` 失效缓存，确保用户主动触发的动作一定取到最新数据。

### ⚠️ 安全：users 集合不落盘

云端 `query` 会**明文返回 password 字段**（见 `api.js` 文件头注释）。若把这批数据写入 localStorage，等同于把凭据明文留在磁盘上。因此 `users` 只做内存缓存——它仅 51KB / 约 340ms，主要收益（同会话内多处共享）不受影响。

## 四、界面呈现

仪表盘标题栏显示「数据更新于 HH:MM:SS」，时间戳取自**缓存中数据的真实取数时刻**（`cache.cachedAt`），而非渲染时刻——否则冷启动读到磁盘旧数据时，会把陈旧数据显示成"刚更新"，属于误导。

## 五、测试

新增 `test/cache.test.mjs`，17 项覆盖：

- TTL 命中与过期（用可控假时钟精确验证，不依赖真实 sleep）
- 并发去重：三个并发请求只发一次网络请求
- SWR 冷启动语义：先返回磁盘旧值，后台刷新后返回新值
- 会话内过期走阻塞刷新（保证「刷新」按钮生效）
- 未过期的磁盘数据直接命中、不触发后台刷新
- 按前缀失效且不影响其他分组
- 内存与 localStorage 同步失效
- `persist:false` 不落盘
- 超大值不落盘（避免阻塞主线程与撑爆配额）
- 配额不足时淘汰最旧数据且不抛错
- localStorage 不可用时降级为内存缓存
- 损坏的 localStorage 数据被当作未命中
- 后台刷新失败静默、不产生未处理的 Promise 拒绝

另有 `test/api.test.mjs` 在接入缓存后补充了**用例间清缓存**的隔离处理——否则前一个用例缓存的数据会被后一个用例命中，导致本用例 mock 的 fetch 根本没被调用（例如期望抛超时却直接返回旧数据）。

## 六、注意事项

1. **数据非实时**：普通浏览时数据最多滞后一个 TTL（60 秒）。需要最新数据请点「刷新」。
2. **多端共享**：数据仍以云端为准；手机端或他人修改后，本地最多 60 秒内可见（点刷新可立即同步）。
3. **磁盘占用**：缓存约占 1.7MB，位于 localStorage；配额不足会自动淘汰最旧数据，不会撑爆。
4. **排查异常**：在控制台执行 `api.clearCache()` 可清空全部本地缓存。
